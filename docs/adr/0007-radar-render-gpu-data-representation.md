# ADR-0007: Storage-buffer + radial-index lookup-texture GPU representation for polar radar rendering

Status: Accepted

## Context
S03 (`crates/radar-render`) had to prove, before any later stage commits to a final interactive renderer, that a `wgpu` (ADR-0002) GPU representation of a decoded NEXRAD sweep can be rendered at interactive frame rates while satisfying `GLOBAL_CONTRACT.md`/`RADAR_TECHNICAL.md`'s hard constraints: the representation must support irregular radial spacing and missing/partial radials, missing and range-folded gates must render distinctly from valid data (never as a plausible-looking fabricated value), nearest-gate mode must exist and be the default, and there must be no per-gate map polygons. The S03 stage doc names three candidate GPU representations to weigh: a plain 2D texture indexed by `(radial, gate)`, a storage/structured buffer, and an optional radial-index lookup texture.

## Decision
Implemented a hybrid of two of the three candidates:

1. **A storage-buffer representation of one sweep's one moment** (`crates/radar-render/src/sweep_buffers.rs`): a flat `GpuRadialMeta` array — one entry per radial that actually carries the requested moment (REF), in original scan order, with azimuth/elevation angle, first-gate range, gate spacing, gate count, and an offset into a second, shared flat `GpuGateSample` array holding every one of those radials' gates back-to-back. Radials without the requested moment are simply absent from the array, not zero-filled or interpolated in — this is what lets the representation support irregular radial spacing and missing/partial radials without assuming a fixed grid. Each `GpuGateSample` carries a pre-converted physical `value` (f32) plus a `flag` (`GATE_FLAG_VALID` / `GATE_FLAG_MISSING` / `GATE_FLAG_RANGE_FOLDED`) that preserves `radar_types::GateValue`'s missing/range-folded distinction unchanged onto the GPU side; the shader (`shaders/radar_sweep.wgsl`) branches on this flag before ever treating a gate as a valid reading.
2. **A 1D radial-index lookup texture** (`crates/radar-render/src/lookup_texture.rs`): 3600 texels (one per 0.1 degrees of azimuth — five times finer than WSR-88D's finest native resolution, so no on-screen bucket boundary is coarser than the radar's own angular resolution), each holding the index of the nearest radial to that bucket's center azimuth, or a documented sentinel (`u32::MAX`) when no radial is within tolerance (a partial-scan gap). This lookup table is built by calling `radar_geo::find_radial_index` directly for every bucket — reusing that function's already-documented and already-tested "nearest radial by circular azimuth distance, tolerance derived from the sweep's azimuth resolution" convention rather than reimplementing azimuth matching a second time. In the shader, this turns per-pixel azimuth-to-radial resolution into a single `textureLoad`, with the sentinel checked explicitly and rendered as no-data rather than falling through to "radial 0".

The shader resolves range-to-gate within a matched radial using the same half-open-interval convention as `radar_geo::find_gate_index` (`[center - spacing/2, center + spacing/2)`), computed directly against the flat local site-relative plane rather than true slant range/geodesy — see `shaders/radar_sweep.wgsl`'s header comment for that documented scope boundary. There is no interpolation anywhere in the lookup path (radial-to-radial or gate-to-gate); nearest-match is the only mode this prototype implements, satisfying "nearest-gate mode must exist and be the default" by making it the only mode. A missing gate renders fully transparent; a range-folded gate renders as a reserved flagged color (opaque magenta) that the REF palette ramp can never itself produce, so it is visually distinguishable from both "valid" and "no data" — never silently treated as either.

## Alternatives
- **A plain 2D texture indexed directly by `(radial, gate)`** (the third stage-doc candidate): **not implemented.** A 2D texture requires a fixed, uniform grid — a constant number of gates per row and, implicitly, a constant/predictable mapping from row to azimuth. Real NEXRAD sweeps do not reliably provide that: azimuth spacing is not perfectly uniform (real radials jitter around the nominal 0.5/1.0 degree spacing, as `radar-geo`'s own irregular-spacing tests document), and a partial scan can be missing radials outright. Building a `(radial, gate)` texture from ragged, possibly-gapped real data means resampling it onto a fixed grid first — exactly the kind of interpolation `GLOBAL_CONTRACT.md` warns against, since resampling a partial scan's gaps or filling a ragged gate-count mismatch risks turning a genuine "no data" cell into a fabricated interpolated value. The storage-buffer representation has no such grid to fill in the first place: a missing radial is an absent array entry, not an empty cell that needs a value.
- **Raw wire encoding shipped to the shader (no CPU-side float conversion) with scale/offset resolved per-pixel in WGSL**: also compatible with the storage-buffer + lookup-texture hybrid (the stage doc explicitly allows either this or the pre-converted-float approach) — not implemented because it would move ordinary, easily-unit-tested scale/offset arithmetic out of Rust and into WGSL, where it cannot be exercised by this crate's no-GPU-required CPU tests. Pre-converting once at buffer-build time keeps that conversion logic in `sweep_buffers.rs`, fully covered by `cargo test --workspace` with no GPU present, while the missing/range-folded distinction still survives to the shader as an explicit flag rather than being collapsed.
- **No lookup texture — a per-pixel linear/binary search over `radial_meta` for the nearest azimuth**: would still support irregular spacing and partial scans (same storage buffer), but repeats an O(radial count) or O(log(radial count)) search per pixel instead of the lookup texture's O(1) `textureLoad`. Not measured head-to-head in this stage (out of scope: the task specified building the lookup-texture hybrid, not re-litigating whether to include it), but a per-pixel search over up to 720 radials at megapixel resolution is the kind of cost the stage doc's "optional radial-index lookup texture" candidate exists to avoid.

## Consequences
**Benefits**: the representation directly satisfies "support irregular radial spacing and missing/partial radials" by construction (absence, not resampling); missing/range-folded gates are structurally distinguishable from valid data all the way from `radar_types::GateValue` through to the fragment shader's branch, so there is no code path that can silently turn either into a plausible-looking value; reusing `radar_geo::find_radial_index`'s exact matching convention means the lookup table's notion of "nearest radial" cannot silently drift from the convention already documented and tested in `radar-geo`; the O(1) lookup-texture resolution keeps the shader's per-pixel cost flat regardless of radial count.

**Costs/risks**: two storage buffers plus a lookup texture is more GPU state to manage than a single 2D texture would have been, and the lookup table must be rebuilt (a CPU-side pass over every radial azimuth) whenever the sweep changes — cheap for one sweep (720 radials x 3600 buckets is a few million cheap comparisons, sub-millisecond in practice) but a cost a plain texture upload would not have had. The 3600-texel lookup resolution is a fixed choice for this prototype; a future stage supporting radars with different native azimuth resolution should confirm 3600 (0.1 degree) is still fine enough, though it already has 5x headroom over WSR-88D's finest mode.

**Scientific implications**: none beyond what is already true of `radar_geo`'s own documented conventions — this stage reuses them rather than introducing new geometric approximations. The shader's flat-local-plane range math (ground range treated as directly comparable to gate range) is a documented scope simplification for this rendering proof only (see `shaders/radar_sweep.wgsl`), not a claim about real slant-range geometry; resolving a real geographic cursor to azimuth/range through Earth curvature remains `radar-geo`'s job (ADR-0006), unaffected by this decision.

## Validation
Measured with `cargo run -p radar-render --bin harness --release` on this development machine (NVIDIA GeForce RTX 5070, Vulkan backend, Windows), against the real `fixtures/nexrad-level2/KTLX20240601_000353_V06` fixture's lowest-elevation sweep carrying REF (elevation 0.48 degrees, 720 radials, 858,240 gate samples, 300.00 km max range):

- **GPU upload time** (CPU buffer build + `wgpu` upload of both storage buffers, the lookup texture, the palette texture, and pipeline/render-target setup): ~18-33 ms across repeated runs.
- **Frame time / FPS**, rendering 1024x1024 off-screen with a per-frame varying camera (simulated pan/zoom), 120 frames, each measurement including a blocking wait for GPU completion (a conservative, non-pipelined measurement — there is no swapchain in this off-screen harness to double/triple-buffer against): average ~0.09 ms/frame (~10,800 FPS), worst observed frame ~0.66 ms (~1,500 FPS) — comfortably past the stage's "~60 FPS interaction on representative hardware" target on this hardware.
- **Palette-switch time** (rewrite the 256-texel palette texture in place + one re-render): ~0.09 ms — well under the stage's 50 ms target.
- **Estimated VRAM footprint** (sum of this harness's own allocations, not a driver query): ~6.6 MiB for the sweep's two storage buffers + lookup texture, ~1 KiB for the palette texture, 96 bytes for the uniform buffer, 4 MiB for the 1024x1024 RGBA8 off-screen render target — about 10.6 MiB total.
- **Visual check**: the saved reference frame (`target/radar-render-harness/ktlx_ref_sweep.png`, not committed) was inspected directly. It shows a mostly-transparent field (correctly rendering the great majority of the sweep as no-data) with a patchy, scattered reflectivity pattern near the site (consistent with near-radar clutter/light returns, including a handful of magenta range-folded-flagged specks rendering distinctly from the green valid-data color), plus two larger, spatially coherent green blobs further from the site consistent with real weather echoes — not a solid fill and not unstructured noise.

These numbers are from one machine with a capable discrete GPU and are illustrative of the representation's feasibility, not a cross-hardware performance guarantee; a lower-powered integrated GPU (a more realistic "representative hardware" baseline for a broader deployment target) has not been measured and should be checked before this decision is treated as fully validated for that class of hardware. `cargo test --workspace` exercises every CPU-side construction path (buffer layout, lookup-table sentinel/wraparound/irregular-spacing behavior, palette LUT construction) with no GPU required, plus one `#[test]` that runs this full GPU pipeline once and asserts the rendered output is not a single uniform color; that test passed against the real adapter above and is structured to print a visible skip (not fail, not silently `#[ignore]`) on a GPU-less CI runner.
