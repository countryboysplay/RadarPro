# ADR-0008: Live NEXRAD Level II data pipeline architecture (`crates/radar-cache`)

Status: Accepted

## Context
S04 requires the first half of `discover -> download -> verify -> cache -> decode -> GPU upload -> render` (the MapLibre/GPU-upload/render half is a separate follow-up task): a WSR-88D site directory, current Level II object discovery against the current public NOAA Open Data Dissemination successor bucket, download with an atomic on-disk cache, retries, cancellation, a background update loop, and basic scan history. This is the first stage in the project to need an async runtime and the first to add an outbound network dependency at all, so it is also the first place three load-bearing choices have to be made explicitly: how to talk HTTPS without a C toolchain (this environment has none — confirmed empirically: no `cl`/`gcc`/`clang`/`cmake`/`nasm` on `PATH`), what retry/backoff policy is "reasonable" absent a spec, and how the on-disk cache stays safe across a crash or cancellation mid-write. `GLOBAL_CONTRACT.md` also constrains all of this: remote data is untrusted until it verifiably decodes, no uncontrolled panics on malformed input, the UI thread must never synchronously decode a complete volume, and stale network/decode work must be cancellable.

## Decision

### Async runtime and HTTP/TLS stack
`tokio` (`=1.47.1`) is the async runtime, with only the features this crate's own code uses enabled (`rt`, `time`, `fs`, and `macros` — the last because `tokio::select!` itself is macro-generated by the `tokio-macros` proc-macro crate gated behind that feature; verified empirically, not just from documentation, that a build with only `rt`/`time`/`fs` fails to compile a `select!` call with "cannot find `select` in `tokio`"). `reqwest` (`=0.13.5`) is the HTTP client, built with `default-features = false` and only the `rustls-no-provider` feature.

`rustls-no-provider` (not `rustls`, reqwest's own default-enabling feature) is the deliberate choice here: `reqwest`'s plain `rustls` feature pulls in `aws-lc-rs` as the default `rustls` crypto provider, and `aws-lc-rs` needs `cmake` plus a C/C++ toolchain to build `aws-lc-sys` — unavailable in this environment, for the exact same underlying reason `nexrad-level2` chose `bzip2-rs` over `bzip2-sys` (ADR context: a decode-only, pure-Rust bzip2 implementation, to avoid a native build dependency this environment cannot satisfy). `rustls-no-provider` instead pulls in `rustls-platform-verifier` (OS-native certificate validation via already-present OS APIs, no C compilation) without forcing a crypto-provider choice, and this crate explicitly installs the `ring` provider (`rustls = { features = ["ring", "std", "tls12"] }`) once per process before any TLS connection (`net::ensure_crypto_provider_installed`, called from `S3Client::new`). `ring` was verified empirically in this exact environment to build cleanly with no C compiler present (it ships precompiled/pregenerated assembly for common targets, including `x86_64-pc-windows-msvc`) and to complete a real HTTPS `GET` against `https://unidata-nexrad-level2.s3.amazonaws.com` successfully.

`quick-xml` (`=0.42.0`) parses `ListObjectsV2` XML responses via its pull-parser API (no `serde`-XML derive needed for the handful of fields read). `serde`/`serde_json` back both the embedded site directory and the on-disk cache sidecar metadata. `tokio-util` (`=0.7.19`, `default-features = false`) supplies `CancellationToken` — its `sync` module needs no optional feature, since `tokio-util` unconditionally depends on `tokio`'s `sync` feature itself.

### Discovery, retry, and backoff
Discovery (`ListObjectsV2`, `S3Client::discover_day`/`discover_latest`) is a distinct module from download (`GetObject`, `cache::download_and_cache`), per the S04 stage brief's "separate object discovery from fetching/decoding so alternate sources remain possible" — discovery never fetches an object body, and download never lists a bucket.

A single retry/backoff policy (`net::BackoffPolicy::DEFAULT`) is shared by both: 5 attempts total, starting at a 500ms delay before attempt 2 and doubling on each further attempt, capped at 8s per delay (worst case `500ms + 1s + 2s + 4s = 7.5s` of sleeping across the 4 retries in a 5-attempt run). These numbers are an engineering judgment call, not sourced from any spec: chosen to give a flaky connection several real chances to recover while keeping the worst case (well under 10s of actual backoff sleeping, plus whatever the underlying requests themselves take, bounded by a 20s per-request client timeout) comfortably under a minute, so a UI waiting on this call never appears to hang. Only transient-looking failures are retried: connection errors, timeouts, response-body read failures, HTTP 429, and HTTP 5xx. A 404 or any other 4xx is treated as permanent and never retried, since retrying the identical request against the identical non-existent resource cannot succeed.

Verification failure gets its own, separate retry: if a download completes fully over HTTP (200, full body) but `nexrad_level2::decode_volume` rejects it, `cache::fetch_and_verify` re-downloads once more (a fresh `GetObject`, after a short fixed 1s pause) before giving up, on the theory that the corruption may have happened in transit rather than being inherent to the object. This is deliberately not folded into the network-level backoff policy above — a decode failure is not a network signal, and repeatedly re-downloading a genuinely bad object cannot fix it, so the cap here is a single extra attempt, not an exponential series.

`ListObjectsV2` pagination (`IsTruncated`/`NextContinuationToken`) is followed correctly rather than truncated at the default 1000-key page size, with a hard `MAX_PAGES = 1000` ceiling purely as a termination guarantee against a misbehaving/adversarial server that never stops paginating — never expected to be reached by real data (a WSR-88D day is at most a few hundred keys, well under even one page).

### Cache layout and atomicity
The cache is a plain directory tree, not a database or a single index file: `{cache_root}/{ICAO}/{filename}` holds the raw Archive II bytes for one volume, and a sidecar `{cache_root}/{ICAO}/{filename}.meta.json` holds the small amount of metadata `scan_history` needs (site, source key, start time, size). Scan history (`cache::scan_history`) is derived purely by scanning these sidecar files, rather than maintained as a separate mutable index — this avoids any need for cross-task locking around shared index state, since two background loops for two different sites only ever touch their own `{ICAO}/` subtree, and a corrupt or missing sidecar is simply skipped (treated as "not cached yet"), never a hard error.

Every write to a cache path (the data file, and the sidecar) goes through write-then-rename: bytes are written in full to a uniquely-named temp file beside the final path (same directory, so the rename stays on one filesystem), then renamed into place. `tokio::fs::rename` (`std::fs::rename` under the hood) was confirmed to replace an existing destination file, not just fail, on this project's Windows target (`MoveFileExW` with `MOVEFILE_REPLACE_EXISTING`, matching POSIX `rename(2)`'s atomic-replace semantics) — this is what makes "just always overwrite the final path via rename" safe cross-platform rather than a Unix-only assumption. A crash or cancellation between the write and the rename leaves, at worst, an orphaned `*.tmp-*` file next to a cache entry; the final path itself is only ever observed as either absent, its previous complete contents, or its new complete contents — never partial.

Bytes are verified (`nexrad_level2::decode_volume` succeeds) strictly *before* the atomic write, not after: a file that downloads completely but fails to decode is never renamed into the cache directory at all, so there is no window in which a bad file is visible at its final path even transiently.

### What the cache holds
The cache stores verified-good **raw bytes**, not decoded, memory-resident `radar_types::Volume` values. `ARCHITECTURE.md`'s concurrency pipeline (`network -> download queue -> decode workers -> decoded cache -> GPU upload queue -> renderer`) and ADR-0005 describe an eventual in-memory decoded cache; this crate's disk cache is the layer that feeds that future decode-worker stage, not a replacement for it. Archive II bytes are already a compact on-disk representation, while a decoded `Volume` is a substantially larger in-memory structure (per-gate vectors across every radial of every sweep); keeping every cached volume decoded and resident at once was rejected as unnecessary and memory-unbounded for what S04 asks this crate to do. Decoding is deferred to `cache::load_cached_volume`, an explicitly synchronous, non-`async` function a caller must run off its own hot/UI path (`spawn_blocking` or equivalent) — kept synchronous rather than wrapped in `async fn` specifically so that obligation stays visible at the call site instead of being silently hidden behind an `.await`, per `GLOBAL_CONTRACT.md`'s "UI thread must not synchronously decode complete radar volumes."

### Cancellation
Every discovery/download/retry-wait/background-poll operation takes a `tokio_util::sync::CancellationToken` (or, for the background loop, owns one via `UpdateLoopConfig`/`run_update_loop`'s caller) and races it against every network attempt and every backoff/poll sleep via `tokio::select!`. Cancelling promptly abandons in-flight work rather than letting a retry loop or a poll sleep run to completion — this is how a caller stops a stale site's download/update loop the moment the user switches to a different site, rather than leaving it consuming bandwidth or CPU in the background.

## Alternatives
- **`native-tls` (OpenSSL binding)**: rejected outright — needs a C toolchain and, on Windows, either a vendored OpenSSL build or a system one, neither available here.
- **`reqwest`'s default `rustls` feature (`aws-lc-rs` provider)**: rejected — needs `cmake` and a C/C++ compiler to build `aws-lc-sys`, unavailable in this environment (the same class of constraint that ruled out `bzip2-sys` for `nexrad-level2`). `rustls-no-provider` + explicit `ring` was verified to build and to complete a real request instead.
- **A single shared mutable cache index file** (e.g. one JSON/SQLite file per cache root listing every cached volume) instead of per-volume sidecars: would let `scan_history` avoid a directory scan, but introduces a second atomicity problem (the index itself needs safe concurrent read/write across possibly-multiple background loops/processes) on top of the one this ADR already has to solve for cache entries themselves. Per-sidecar metadata sidesteps that entirely: each write is independently atomic, and history is a read-only scan with no shared mutable state to corrupt.
- **Caching decoded `Volume`s (e.g. via `bincode`) instead of raw bytes**: would let a cache hit skip decoding entirely, but requires either introducing a new binary serialization dependency and format-versioning story for `radar_types::Volume`, or keeping every cached volume decoded in memory at once (memory-unbounded, and unnecessary before a real GPU-upload/render consumer exists to actually need decoded data resident). Raw-bytes-on-disk plus decode-on-demand was chosen instead; see "What the cache holds" above.
- **A jittered/randomized backoff** instead of plain exponential: not used — with only 5 attempts and a single client per operation (not a fleet of clients hammering S3 in lockstep, which is what jitter primarily defends against), the added complexity was judged not worth it for this stage; documented here as a candidate a future stage could add if real-world retry storms are ever observed.

## Consequences
**Benefits**: no C toolchain is required anywhere in this crate's dependency tree, verified empirically rather than assumed; discovery and download stay independently testable and independently swappable (a future alternate Level II source could implement discovery differently without touching download/cache/verify); the atomic-write/verify-before-cache design means a partially downloaded or corrupted file can never reach a consumer as if it were good data, satisfying `GLOBAL_CONTRACT.md`'s untrusted-remote-data rule at the one boundary (this crate) where network bytes cross into the rest of the system; cancellation is threaded through every layer (single request, retry loop, background poll loop) rather than bolted on only at the outermost call, so a site switch actually stops in-flight work rather than merely stopping new work from starting.

**Costs/risks**: the sidecar-per-volume design means `scan_history` is O(files in the directory) rather than O(1) index lookup — acceptable at the scale of "recent scans for one site" (at most a few hundred per day) but would not scale to indexing years of retained history without a real index; the verify-then-retry-once policy adds up to one extra full download (several MB) for a volume that turns out to be genuinely undecodable (not just transient corruption), which is a deliberate bandwidth-for-reliability tradeoff; `ring`'s reliance on precompiled/pregenerated per-target assembly means an *unsupported* target this project might target in the future (an exotic embedded target, say) could reintroduce the C-compiler dependency this ADR works around today — worth re-checking if/when new target platforms are added.

**Reliability implications**: directly implements the two `GLOBAL_CONTRACT.md` rules this stage exists to satisfy for the live pipeline: "remote data is unreliable and untrusted" (nothing is cached without decoding successfully first) and "cancellation/deprioritization is required for stale network/decode work" (every layer is cancellable). It also sets up the next stage (GPU upload/render integration) to satisfy "the UI thread must not synchronously decode complete radar volumes" by keeping decode-from-cache an explicit, visible, non-`async` call a future caller must deliberately move off its UI thread, rather than hiding it inside something that looks safe to call inline.

## Validation
`cargo test --workspace` passes cleanly (`cargo fmt --all -- --check`, `cargo clippy --all-targets -- -D warnings`, and `cargo build --workspace` all clean too). `crates/radar-cache`'s 37 unit tests cover: all 159 real WSR-88D sites loading with two spot-checked against known ground truth (KTLX, KFTG — both already meaningful in this repo via their S01 fixture volumes); `ListObjectsV2` XML parsing against synthetic-but-structurally-real fixtures for a normal response, a paginated/truncated response, an empty result, and multiple classes of malformed/truncated XML (including a case only caught by this crate's own open-element-depth tracking, since `quick-xml`'s pull parser was confirmed empirically to *not* itself error on a document that simply stops mid-tag at EOF); object-key filtering (`_MDM` and non-`_V0[2-7]` suffixes excluded, valid keys parsed and sorted correctly); atomic-write behavior under a simulated interrupted write (a `.tmp-*` file written and never renamed, confirming the final path is never exposed with partial content); and background-loop cancellation stopping promptly rather than running to completion.

One test (`tests/live_network.rs`) exercises the real network end to end, following the same pattern already established for GPU availability in `crates/radar-render/src/gpu_tests.rs`: any failure (no network, NOAA's service unavailable, or — as it happens — a decode/verification failure) is treated as a clear, printed skip rather than a suite failure, so an offline or sandboxed CI runner is never made flaky by this test. Run with real network access available in this environment: discovery correctly found 234 real scans for KTLX for the current UTC day (confirming discovery, pagination, and key-filtering all work against live production data, not just fixtures) and download completed successfully; the downloaded object failed `nexrad_level2::decode_volume` verification with `unsupported message type 32` — current live WSR-88D production traffic apparently now includes a message type this project's S01 decoder does not yet support (confirmed this is not a stale-archive artifact: the exact 2024 fixture key this repo already ships, `KTLX20240601_000353_V06`, is still present and unchanged in the live bucket, so the gap is specific to *current* production data, not this bucket generally). This is a real, useful finding for a future `nexrad-level2` stage, and it is exactly the scenario this ADR's verify-before-cache design exists to handle correctly: the bad-format object was downloaded, rejected by verification, retried once, rejected again, and never written to the cache directory — proving the "never cache what doesn't verifiably decode" contract holds against genuine current real-world data, not just synthetic test cases.
