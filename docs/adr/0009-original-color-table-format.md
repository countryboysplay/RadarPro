# ADR-0009: An original, documented, user-editable color-table format

Status: Accepted

## Context
`RADAR_TECHNICAL.md` requires that "RadarPro should use an original documented format supporting units, product compatibility, stepped/gradient mappings, alpha, missing, and range-folded states." S05's stage doc adds "user-editable original color-table format" to the workstation's feature list. Until now, `crates/radar-render/src/palette.rs` shipped exactly one hardcoded ramp — a fixed `Vec<PaletteStop>` for REF (reflectivity) only, explicitly documented as "an example placeholder ramp for the S03 rendering proof, not RadarPro's real color-table format." S05 needed a real format before it could support a moment/elevation picker meaningfully: VEL, SW, ZDR, CC, and PHI all need their own, physically-appropriate palettes, and `GLOBAL_CONTRACT.md`'s branding rule ("its own branding, UI, assets, defaults, and algorithms") plus this stage's "user-editable" requirement rule out simply hardcoding five more Rust ramps the way the REF placeholder did — a real file format, parseable/validatable from untrusted input, was needed.

`GLOBAL_CONTRACT.md`'s reliability rules ("no uncontrolled panics on malformed input," written about remote radar data) and this project's general "never trust untrusted input" discipline apply equally to a user-edited local file: a hand-edited or hand-crafted color-table JSON file is exactly as untrusted as a byte stream fetched over the network, just from a different source.

## Decision
Added `crates/radar-render/src/color_table.rs` (`ColorTable`, `ColorTableMode`, `ColorTableDomain`, reusing `palette::PaletteStop` as `ColorStop`) implementing a new, original JSON format — fully specified in `crates/radar-render/COLOR_TABLE_FORMAT.md` and summarized here:

- **JSON**, chosen because `serde`/`serde_json` are already pinned dependencies elsewhere in this workspace (`radar-cache`), this project already treats JSON as its default structured-data format, and JSON is trivially human-readable/hand-editable with no custom parser or binary tooling required — directly serving the "user-editable" requirement.
- **`format_version`**: an explicit integer, checked exactly (not "at least"), so a future incompatible format change fails loudly on an old file instead of silently misinterpreting it.
- **`moments`**: an array of `MomentKind::wire_code` strings (`REF`/`VEL`/`SW`/`ZDR`/`CC`/`PHI` — a small, narrowly-scoped addition to `radar-types` itself, see "Scope note" below) declaring which moment(s) a table is compatible with — "product compatibility."
- **`units`**: a free-text physical unit string (`"dBZ"`, `"m/s"`, `"dB"`, `"deg"`, `"dimensionless"`) carried alongside the table purely as documentation (this format does not convert units — `GLOBAL_CONTRACT.md`: "display-unit changes never mutate source data") but load-bearing documentation: a UI or a probe result can always report what unit a value is already expressed in.
- **`mode`**: `"gradient"` (continuous linear interpolation, reusing `palette::sample_stops`) or `"stepped"` (discrete, held-color buckets — the traditional NWS look; a new `palette::sample_stops_stepped`, added alongside the existing gradient sampler rather than replacing it).
- **`domain`**: an explicit `{min, max}` the built LUT covers, replacing the hardcoded `DEFAULT_REF_MIN_DBZ`/`DEFAULT_REF_MAX_DBZ` constants for the general case (those two constants are kept, now describing only the REF default's own domain).
- **`cyclic`**: a boolean (default `false`) for PHI's 0–360 degree wrap-around; `true` wraps out-of-domain input with `rem_euclid` and, in gradient mode, interpolates smoothly across the `domain.max`/`domain.min` seam instead of clamping to an endpoint.
- **`stops`**: an array of `{value, color}` (color always `[r, g, b, a]`, alpha included, so a table can express partial transparency at low signal — not just fully-opaque-or-fully-transparent), validated non-empty, strictly ascending by value, each value finite and within `domain`.
- **`missing_color`/`range_folded_color`**: two dedicated top-level fields, structurally separate from `stops` — the code that maps a physical value to a color (`build_lut_from_table`, generalizing `palette::build_palette_lut`) never reads either field at all, so there is no code path by which a value lookup could ever produce one. The one validated rule between them is that they must differ from each other (a legend must be able to show two distinct states); they are *not* required to differ from any of `stops`' own colors, since a table may legitimately give a below-threshold "real but very weak" stop the same fully-transparent appearance as "no data" (as REF's and SW's own defaults do) — an intentional design choice, not an ambiguity, because the underlying `radar_types::GateValue`/`sweep_buffers::GpuGateSample::flag` distinction survives through a completely separate channel regardless of what color anything is drawn in.
- Parsing uses `#[serde(deny_unknown_fields)]` throughout, so a typo'd field name in a hand-edited file is a load error, not a silently ignored field — `ColorTable::from_json` returns a structured `ColorTableError` (never panics) for any malformed input: bad JSON syntax, wrong/unsupported `format_version`, an unknown moment code, an invalid domain, empty/unsorted/out-of-range stops, or `missing_color == range_folded_color`.
- Shipped six built-in default tables under `crates/radar-render/color_tables/*.json` (REF, VEL, SW, ZDR, CC, PHI) — these files *are* the defaults (loaded via `include_str!` + `ColorTable::from_json`, not duplicated as a second Rust-literal copy) and are simultaneously this format's worked examples. REF's default is a byte-for-byte port of the pre-existing S03 placeholder ramp (verified by a test asserting equality), so switching S05 rendering from the old hardcoded path to this table changes nothing visually for REF. The other five are new, informed-but-not-scientifically-derived design choices, documented briefly:
  - **VEL**: diverging green (strong inbound, −32 m/s) → gray (near zero) → red (strong outbound, +32 m/s), the traditional NWS base-velocity look.
  - **SW**: single-hue teal → blue → purple, 0–15 m/s, with a transparent sub-1 m/s floor mirroring REF's own "no signal" treatment.
  - **ZDR**: blue → cyan → green → yellow → orange → magenta-ish red, −2 to 8 dB.
  - **CC**: a wide, muted low end (0.0–0.8) and most of the visual range concentrated between 0.8 and 1.05, since "a narrow high-value range is where the interesting structure is" (`RADAR_TECHNICAL.md`).
  - **PHI**: a cyclic six-color hue wheel (red → yellow → green → cyan → blue → magenta → back to red), `domain = [0, 360]`, `cyclic = true`, first and last stops sharing a color for a seamless loop.
- Exposed through `radar-web`'s wasm API: `RadarWebRenderer::loadColorTable(json)` (parse + validate + apply to every moment the table names), `activeColorTableJson(momentCode)` (read back the active table, custom or default, for display/editing), and `resetColorTable(momentCode)` (revert to the built-in default).

**Scope note (narrow `radar-types` change):** added `MomentKind::wire_code`/`MomentKind::from_wire_code`/`Display` to `crates/radar-types/src/lib.rs`. This format (and `radar-web`'s wasm API) both need a stable, short, string identifier for a moment kind; that mapping belongs once on `MomentKind` itself, not duplicated ad hoc in `radar-render` and `radar-web` separately. No other `radar-types` behavior changed.

**Not implemented (documented, not silently dropped):** `shaders/radar_sweep.wgsl` still renders missing/range-folded gates with its own fixed, hardcoded reserved colors (transparent / opaque magenta), independent of any color table's `missing_color`/`range_folded_color` fields. This is deliberate, not an oversight: it is a *stronger* guarantee than reading a per-table color at render time (the reserved colors cannot vary even if a maliciously or carelessly authored table tried to make them collide with something), and rewiring the shader/uniform layout to source these two colors from the active table was judged out of scope for this stage — the format itself is still fully self-describing without that wiring (a table shipped alone still documents its own missing/range-folded appearance for a legend). A future stage may choose to wire these through if per-table missing/range-folded colors are wanted in the actual render, not just in a legend.

## Alternatives
- **A binary/proprietary-style palette file** (the style used by some commercial radar-display tools, e.g. fixed-size headers with fixed dBZ breakpoints and no self-declared units/moment-compatibility metadata): rejected. `GLOBAL_CONTRACT.md` requires RadarPro to have "its own branding, UI, assets, defaults, and algorithms," and a binary format is neither human-editable (this stage's explicit requirement) nor self-documenting — a user cannot hand-write or diff it, and it would need custom (non-`serde`) parsing code. This format differs from that style in every load-bearing way: it is text, it is self-describing (every field has a name, not a positional byte offset), and it declares its own units/moment-compatibility/mode/missing-and-range-folded semantics explicitly rather than assuming a fixed, tool-specific convention the reader must already know.
- **A general-purpose scientific colormap format (e.g. matplotlib-style named colormaps, or a bare list of RGB stops with no metadata)**: rejected as insufficient on its own — it has no place to declare moment compatibility, units, a stepped-vs-gradient mode, or (critically) a structurally distinct missing/range-folded color, all of which `RADAR_TECHNICAL.md` explicitly requires. RadarPro's format can be *seeded* from such a colormap's raw RGB stops (paste them into `stops`), but a raw stop list is not itself a complete table under this ADR.
- **A GIS styling format (e.g. an SLD/QML-style raster color-ramp definition)**: rejected as a poor fit — those formats are designed around a general GIS rendering pipeline (arbitrary raster bands, no native concept of a *radar* moment, physical unit, or a range-folded state) and adopting one would mean bending radar-specific semantics into a vocabulary built for something else, rather than defining the small, precise vocabulary this domain actually needs.
- **Reusing `palette::PaletteStop`'s existing ad hoc shape with no surrounding format**: rejected — stops alone cannot express moment compatibility, units, mode, domain, or missing/range-folded colors; every one of `RADAR_TECHNICAL.md`'s named requirements needs a field this ad hoc shape does not have. (The stop type itself *is* reused directly, `pub type ColorStop = palette::PaletteStop`, rather than duplicated — see the Decision section.)

## Consequences
**Benefits**: one documented, versioned, self-validating format covers every moment this project currently decodes (REF, VEL, SW, ZDR, CC, PHI) instead of one hardcoded Rust ramp; a user (or a future in-app editor, out of scope for this stage) can hand-write or hand-edit a table from `COLOR_TABLE_FORMAT.md` alone; malformed input is always a structured `ColorTableError`, never a panic; the missing/range-folded separation is enforced at the type level, not by convention; the six shipped defaults double as both the product's real defaults and the format's own worked examples, so they can never silently drift apart.

**Costs/risks**: the format's `cyclic` gradient wrap-around logic (extending the stop list with two virtual boundary stops) is new, format-specific code with its own edge cases (single-stop tables, non-positive spans) — covered by dedicated unit tests, but it is more logic than the non-cyclic path needed. The current renderer does not source `missing_color`/`range_folded_color` from the active table (see "Not implemented" above); a future stage wiring that through will need to extend `GpuUniforms`/`shaders/radar_sweep.wgsl` and re-verify the never-fabricate guarantee still holds end-to-end after that change. `format_version` is checked for exact equality with no migration path yet — acceptable while there is only one version, but a future breaking change will need a documented upgrade story (e.g. a converter, or supporting a small compatible range) rather than just bumping the constant.

**Scientific implications**: the five new non-REF default palettes (VEL, SW, ZDR, CC, PHI) are informed UI/design choices about color, not scientifically derived thresholds — `RADAR_TECHNICAL.md` explicitly scopes this as a UI decision ("use your own informed judgment for exact default color choices... not a scientific one requiring ground-truth research"), and this ADR's Decision section documents the reasoning behind each. No moment's underlying decoded physical values, scale/offset, or missing/range-folded classification are affected by this format in any way — it is presentation-only, consistent with `GLOBAL_CONTRACT.md`'s "display-unit changes never mutate source data."

## Validation
- `cargo test -p radar-render` — 49 tests, including `color_table`'s: valid-table acceptance for every `MomentKind`; the REF default's byte-for-byte equality with the pre-existing S03 placeholder ramp; every documented validation failure (bad JSON, unknown field, wrong format version, empty name/moments/units/stops, invalid domain, non-finite/unsorted/out-of-domain stop values, `missing_color == range_folded_color`) returning a structured error, never panicking; stepped-vs-gradient interpolation correctness at known sample points (exact expected `lerp` results computed by hand); cyclic gradient/stepped wraparound correctness at known sample points, including the seam itself.
- `cargo test -p radar-web` — `render_select`'s structural proof that decoding a real fixture once and building GPU-buffer input for two different `(elevation, moment)` selections (REF and VEL) never calls the decoder a second time (see ADR context in `crates/radar-web/src/render_select.rs`; this exercises `color_table`'s LUT indirectly via the same code path `RadarWebRenderer::select_and_render` uses).
- `cargo fmt --all -- --check`, `cargo clippy --all-targets -- -D warnings`, `cargo clippy -p radar-web --target wasm32-unknown-unknown --lib -- -D warnings`, `cargo build --workspace` all pass.
- A real-browser check (Chrome via CDP, same approach as S04) loading a real fixture and switching between at least two moments and two elevations, confirming visually distinct rendered output for each, is recorded in `crates/radar-web/README.md`.
