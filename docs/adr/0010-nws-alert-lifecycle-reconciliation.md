# ADR-0010: Poll-race-safe NWS alert lifecycle reconciliation (`crates/weather-alerts`)

Status: Accepted

## Context
S06 requires the core (Rust) half of an NWS alert overlay: a normalized `Alert` model, CAP/GeoJSON parsing of `https://api.weather.gov/alerts/active`, and lifecycle behavior — new alerts, updates/replacements, cancellations, and expiration — that "matches source semantics" (S06 exit criteria). `GLOBAL_CONTRACT.md` adds two hard rules this stage names explicitly: "official alerts are not inferred from radar" (out of scope for this ADR — trivially satisfied by this crate containing no radar-derived logic at all) and "do not let polling races incorrectly resurrect or remove alerts."

That second rule is the actual design problem. A caller of this crate polls `/alerts/active` on some interval (this stage does not fix a cadence; a reasonable assumption, consistent with NWS's public API being a shared resource other consumers also poll, is a poll roughly every 60–120 seconds, not sub-second) and feeds each poll's full parsed response to the store. Every poll is an independent network round trip against a live, third-party HTTP API — subject to timeouts, transient 5xx/empty responses, partial CDN/cache staleness, and ordinary internet flakiness (`GLOBAL_CONTRACT.md`: "Remote data is unreliable and untrusted"). The naive design — "an alert is active iff it appeared in the most recently polled response" — fails this rule directly: a single dropped or slow request would make a real, still-valid tornado warning disappear from the map for one poll cycle and then reappear, which is exactly the "incorrectly resurrect or remove" failure this stage's rule forbids. The reverse failure is just as real: relying purely on "did this id appear in the response" for *removal* means a single malformed/truncated response with a `Cancel` message dropped or reordered could wrongly resurrect an alert that was validly cancelled moments earlier, or a race between two nearly-simultaneous polls (only possible if a caller runs more than one poll loop, but a robust design should not depend on the caller never doing that) could reprocess the same messages out of order.

A second, distinct problem specific to CAP: each message (including an `Update` that only refreshes an existing warning's wording/polygon) carries its own unique CAP identifier, and an `Update`/`Cancel`'s `references[].identifier` names the *immediately preceding* message, not a stable "warning event" id that persists across the whole update chain. A design that keys held state by "the current message's own id" would therefore change a UI-visible feature's identity on every single update.

## Decision

### Two-level identity: stable key vs. latest message id
`AlertStore` (`crates/weather-alerts/src/store.rs`) separates a **stable `AlertKey`** (the id of the *first* message that introduced a given held alert, fixed for that alert's whole lifetime in the store) from the **latest message id** (rotates to the newest message's own `id` on every update, since that is what the *next* update/cancel's `references` will name). An internal secondary index (`latest message id -> stable key`) resolves an incoming message's `references` back to the right held entry regardless of how many updates have happened since the alert was first introduced. A consumer (a MapLibre `geojson` source, a details-panel list) keys its own UI state on the stable `AlertKey`, so an update never causes the corresponding map feature/list row to flicker out and back in under a new id.

### "Update" and "replacement" are the same mechanism
S06 lists "update" and "replacement" as separate test scenarios. Real NWS data (fetched during development from both `?area=OK` and a full national snapshot) confirms `messageType: "Update"` messages that reference a prior message and refresh its content (a Severe Thunderstorm Warning's `SVS` continuation, observed live). No real `messageType: "Cancel"` or hazard-upgrade "replacement" example was present in either live snapshot at fetch time (see `crates/weather-alerts/tests/fixtures/README.md` for why that is expected, not a gap in the sample). Rather than special-casing `messageType == "Update"` specifically, `AlertStore` treats **any** non-`Cancel` message whose `references` names a currently-held alert as content replacement under that alert's existing stable key — whether NWS's own `messageType` for it says `"Update"` or `"Alert"` (the latter covers a hazard-type upgrade, e.g. a Tornado Warning issued as a fresh CAP `Alert` message that still references the Severe Thunderstorm Warning it supersedes). Both are reported to the caller identically as `AlertChange::Updated`. This is a deliberate simplification: it makes "replacement" not a separate code path to get wrong, at the cost of not distinguishing "same hazard, refreshed wording" from "hazard type changed" in the change event itself — a caller that cares about that distinction can still detect it by comparing `alert.event` before/after, since both the old and new content are available.

### Removal requires one of three signals, never bare absence
An alert already held by the store is removed only when:
1. **An explicit `Cancel` message's `references` names it.** Treated as immediately authoritative and never second-guessed — per S06, an explicit cancellation is source-of-truth, and a `Cancel` referencing nothing currently held is a no-op (not an error; the store may simply not have been tracking whatever it names, e.g. it already expired).
2. **Its own `expires` timestamp is no longer in the future**, checked against a caller-supplied `now` both when a poll is ingested (`AlertStore::ingest_poll`) and, independently, at plain query time (`AlertStore::active_alerts`) and via `AlertStore::expire_stale` — so an alert stops being reported active the instant real time passes its `expires`, not merely whenever the next poll happens to notice. `expires` (not the optional `ends`) is the field used for this: see [`Alert::expires`'s doc comment](../../crates/weather-alerts/src/model.rs) for the empirical evidence (152 of 247 real alerts with a non-null `ends` in a national snapshot had `ends` *after* `expires`, sometimes by many hours) that `expires` — CAP's own "this message's technical validity" field — is the correct authoritative signal, not "when the forecaster expects the hazard to end."
3. **The alert has been absent from `AlertStore::DEFAULT_ABSENCE_LIMIT` (3) consecutive `ingest_poll` calls in a row**, with neither of the above having already removed it. This is the secondary safety net for NWS genuinely dropping an alert from the feed without ever sending an explicit `Cancel` (observed as a real operational possibility, not merely theoretical). Bare absence from a *single* poll produces no change at all — the store only reports `AlertChange::Expired { reason: ExpiryReason::AbsentFromPolls }` once three independent, successful poll responses in a row have all agreed the alert is gone. This is not itself a race condition for the same reason a quorum vote is not: a single flaky/incomplete response can trivially cause one false absence, but three consecutive independent HTTP round trips all missing the same still-valid alert is a materially different (and, empirically for a stable single-source HTTP JSON API rather than a lossy peer-to-peer network, very unlikely) failure mode. The counter resets to zero the instant the alert is seen again in any later poll (including an exact idempotent repeat of already-known content), so a transient one-poll gap followed by recovery never accumulates toward removal across unrelated gaps.

`3` was chosen, not derived from a formal model: it is small enough that a genuinely-dropped alert with no `Cancel` is still noticed within a few poll cycles (at an assumed ~60–120s cadence, well under 10 minutes), and large enough that a single bad response, or even two independent bad responses in a row, cannot remove a real alert. `AlertStore::with_absence_limit` exposes this as a constructor parameter rather than a hardcoded constant, since a caller with a very different, well-understood polling cadence (e.g. a much slower or much faster loop) may reasonably want a different N; `AlertStore::new()` uses the default.

### `active_alerts` is a pure read; `ingest_poll`/`expire_stale` mutate
`AlertStore::active_alerts(now)` never mutates the store — it is safe to call as often as a UI wants (every render frame) purely to answer "what's active right now," always re-applying the `expires > now` check at call time. Removal (and the `AlertChange` events a UI reacts to incrementally via `AlertStore::drain_changes`) only happens inside `ingest_poll` and the separately-callable `expire_stale`, which a caller can invoke between polls purely to keep the *change stream* current with real time without waiting for the next network round trip.

## Alternatives
- **"Active iff present in the latest poll"** (no held state at all): rejected outright — this is exactly the race condition `GLOBAL_CONTRACT.md` warns against; a single transient empty/partial response flickers every alert off and back on.
- **Immediate removal on any single absence, no absence counter**: same problem as above in a milder form — still fails on one bad poll.
- **No secondary absence-based safety net at all (only `Cancel` + `expires`)**: simpler, and arguably "more principled" (only ever removing on an authoritative signal), but leaves the store with no recovery path if NWS genuinely stops listing an alert without ever sending a `Cancel` — the alert would sit "active" until its own `expires` lapses regardless of whether it is still real, which for a long-duration product (the same class of product where `expires` and `ends` diverge) could be hours of showing stale information. The 3-consecutive-poll counter was chosen as a bounded, evidence-requiring middle ground.
- **Using `ends` instead of `expires` for time-based removal**: rejected with direct empirical evidence (see Decision, point 2) — `ends` is optional, often absent, and when present is sometimes hours *after* `expires`, which would keep displaying an alert as active well past the point NWS's own message says it is no longer technically valid.
- **A separate `AlertChange` variant for "replacement" distinct from "update"**: considered, but rejected as an unjustified special case — see Decision's "Update and replacement are the same mechanism"; nothing about how a caller would react differs between the two once both `messageType`s are handled by the same reference-matching rule.
- **Keying held alerts by their own current message id (no separate stable key)**: rejected — see Context; would flicker a UI's feature identity on every routine update.

## Consequences
**Benefits**: the store's public contract directly names and defends against the exact failure mode `GLOBAL_CONTRACT.md` calls out ("do not let polling races incorrectly resurrect or remove alerts") rather than merely happening not to exhibit it; a caller gets a stable per-alert identity across an arbitrarily long update chain without any bookkeeping of its own; `active_alerts`/`expire_stale`/`ingest_poll`/`drain_changes` cleanly separate "current snapshot" (pure, cheap, callable anytime) from "what changed" (accumulated, drainable) from "network poll ingestion" (the only place absence bookkeeping advances), which maps directly onto how a map layer (wants the current snapshot) and a details-panel list (wants incremental events) actually consume this data differently.

**Costs/risks**: a genuinely cancelled-but-never-explicitly-`Cancel`-ed alert can take up to `absence_limit` consecutive polls to be removed via the safety net (bounded, but not instant) — acceptable since the far more common and far more damaging failure mode (transient network flakiness wrongly removing a real warning) is what this design prioritizes against; treating any `references`-matching non-`Cancel` message as a content replacement (the "update and replacement are the same mechanism" decision) means this crate does not itself distinguish "same hazard continued" from "hazard type changed" as a first-class signal — a future consumer that needs that distinction (e.g. to play a different alert sound for an upgrade) must compare `event` fields itself; `3` and the "~60–120s poll cadence" assumption underlying it are engineering judgment calls, not measured against real long-running production polling, and should be revisited if a future stage's real-world polling loop turns out to have a very different cadence or a materially different false-absence rate than assumed here.

**Reliability implications**: this design is this stage's direct implementation of `GLOBAL_CONTRACT.md`'s "Remote data is unreliable and untrusted" for the *lifecycle* dimension specifically (as opposed to the *parsing* dimension, which `crates/weather-alerts/src/parse.rs` handles via bounded, never-panicking, per-feature-isolated parsing — one malformed feature in a `FeatureCollection` cannot take down the rest of the batch, mirroring `nexrad-level2`'s established untrusted-input discipline).

### Generalizing beyond NWS alerts
Nothing in `AlertStore`'s design (`Cancel`/reference-based linking, message-validity-based expiration distinct from event-duration fields, N-consecutive-absence as a bounded safety net, stable-key-vs-latest-message-id separation) is NWS-CAP-specific beyond the exact field names it reads. `reference/FUTURE_SCOPE.md`/S12 names SPC convective outlooks and NHC tropical advisories as later official-feed integrations; both are lifecycle problems of the same shape (a periodically-reissued official product that supersedes or expires its predecessor, polled over an unreliable network), and both are very plausibly reachable through the same reconciliation pattern — a future stage should evaluate reusing this crate's `store` module's approach (parameterized over whatever that feed's own "references/supersedes" and "validity" fields are) rather than re-deriving poll-race safety from scratch.

## Validation
`cargo fmt --all -- --check`, `cargo clippy --all-targets -- -D warnings`, `cargo clippy -p weather-alerts --target wasm32-unknown-unknown --lib -- -D warnings`, `cargo test --workspace`, and `cargo build --workspace` all pass (see the S06 core completion report for full output). `crates/weather-alerts/tests/lifecycle.rs`'s 14 tests cover, by name: `initial_warning_introduces_a_new_active_alert`; `update_message_replaces_held_alert_content_under_the_same_stable_key` and `a_second_update_chains_off_the_first_updates_message_id_not_the_original` (update); `alert_type_message_referencing_a_held_alert_is_treated_as_a_replacement` (replacement); `cancel_message_confidently_removes_the_referenced_alert`, `cancel_referencing_nothing_currently_held_is_a_silent_no_op`, and `a_cancel_message_is_never_itself_held_as_an_active_alert` (cancellation); `expiration_removes_an_alert_by_time_even_with_no_new_poll` and `ingest_poll_also_applies_time_based_expiration` (expiration); and directly, the race-safety property itself: `alert_missing_from_one_poll_with_no_cancel_and_not_expired_is_still_active`, `alert_reappearing_after_a_missed_poll_resets_the_absence_counter`, and `alert_absent_for_n_consecutive_polls_is_removed_as_a_safety_net`. `crates/weather-alerts/tests/parse.rs`'s 18 tests cover polygon, multipolygon, and malformed-geometry (garbage coordinates, wrong nesting depth, too-short ring, unsupported geometry type, and — the stage's explicit requirement — one malformed feature not discarding the rest of a batch), plus parsing a real fetched NWS fixture (`tests/fixtures/alerts-active-ok-20260912.json`) end to end, including a real `Update` message's `references` resolving correctly.
